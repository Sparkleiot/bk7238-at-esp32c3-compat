# `AT+PING` 结案报告 — 固件正常，TIMEOUT 来自对端不回 ICMP

- 时间: 2026-10-08
- 被测: COM5（STA，连真实路由 MyHomeWiFi，IP 192.168.0.163，RSSI -38）
- 固件: `at-esp32c3-compat_2M.1220.bin`
- 探针: `tools/ping_probe.py` / `ping_lan_matrix.py` / `ping_gw_loop.py` / `ping_tcp_gw.py`

## 1. 长期悬案

`AT+PING="192.168.0.1"`（模组 → 网关）稳定回 `+PING:TIMEOUT`，与 TCP/UDP 全通的事实相矛盾，
此前被列为「疑似固件 bug」。本报告定性并结案。

## 2. 判据矩阵（模组作为发起方）

| 目标 | 类型 | 结果 | 判定 |
|---|---|---|---|
| `192.168.0.139` | 同网段主机 | **+PING:76** | ✅ 通 |
| `192.168.0.164` | 同网段主机 | **+PING:92** | ✅ 通 |
| `192.168.0.173` | 同网段主机 | **+PING:54** | ✅ 通 |
| `192.168.0.163` | 模组自身 | **+PING:0** | ✅ 通 |
| `8.8.8.8` | 公网 | **+PING:184** | ✅ 通 |
| `www.baidu.com` | DNS + 公网 | **+PING:42** | ✅ 通 |
| `192.168.0.1` | 网关 | `+PING:TIMEOUT` ×6 | ❌ 对端不回 ICMP |
| `192.168.0.152` | 测试 PC | `+PING:TIMEOUT` | ❌ PC 防火墙丢入站 |
| `192.168.0.34` / `.151` / `.187` | 同网段主机 | `+PING:TIMEOUT` | ❌ 主机不开 ICMP / 不在线 |
| `1.1.1.1` | 公网 | `+PING:TIMEOUT` | ❌ 本网络不可达 |

**同网段多台主机 + 自身 + 公网全部 PASS ⇒ 固件的 on-link ICMP 收发、路由、回程链路均正常。**

## 3. 网关那个才是关键 — 并**不是**固件问题

反直觉之处：**同一时刻**从 PC 连续 4 轮 `ping 192.168.0.1` 全部 **0 ms / 0% 丢包**，
而模组 4/4 全 TIMEOUT。为排除「模组到网关的二/三层通路有问题」，做了一次 TCP 判定：

```
AT+CIPSTART=0,"TCP","192.168.0.1",80   ->  0,CONNECT OK
```

**模组能跟网关完成完整 TCP 三次握手** ⇒ ARP 正确、二层/三层双向通路完全正常。
因此网关的 TIMEOUT 只能是**路由器侧不回 ICMP echo**（按客户端/策略选择性不回），与固件无关。

## 4. 附带的对照证据

PC → 模组 `ping 192.168.0.163`：**2/3 回复，TTL=255** ⇒ 模组的 ICMP **应答**路径也正常。

## 5. 结论与后续

- **`AT+PING` 无需任何修改**，撤销「待定性」标签。
- 写 PING 类断言时的判据修正：`+PING:<ms>` 才算通；`+PING:TIMEOUT` **不能单独推出固件故障**，
  必须先确认对端是否回 ICMP（建议固定用 `8.8.8.8` 作为「基准可达」参照）。
- 至此文档 v1.5 验收中**已无任何未定性的固件疑点**：剩余 3 个 FAIL 全部归因于测试机 PC
  的防火墙丢弃入站（详见 `doc_v15_report_final_1008.md`）。
